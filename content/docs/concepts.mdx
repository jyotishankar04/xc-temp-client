title: Concepts

XecureCode organizes reliability work around organizations, services,
incident events, grouped cases, deployments, RCA reports, recovery actions,
and audit logs. These concepts appear in the dashboard, SDK payloads, and
backend API.

## Core concepts

| Concept | Description |
| --- | --- |
| Organization | The top-level workspace that owns services, memberships, audit logs, and GitHub integration. |
| Service | An application plus environment. Services own API keys, events, cases, members, and rollback settings. |
| API key | A service-scoped secret used by SDKs to send failure events to the ingest API. |
| Incident event | A single captured error payload with stack trace, severity, deployment metadata, service context, and optional request context. |
| Failure case | A grouped incident created from related events, usually by fingerprint, deployment, and service context. |
| Deployment | A versioned release record that ties incidents to commit hashes, release metadata, and stable versions. |
| RCA report | An asynchronous AI-assisted explanation for a case, with evidence and reviewer notes. |
| Action | A recommended recovery action that can be approved or rejected by a human reviewer. |
| Rollback | A GitHub workflow-backed recovery path that uses deployment history, rollback configuration, and human approval. |
| Notification | A per-user inbox item that tracks incident updates, approvals, and recovery progress. |
| Audit log | An append-only record of important user, system, and AI actions across the organization. |

## Event lifecycle

1. The SDK captures and sends an incident event.
2. The backend fingerprints and stores the event.
3. Workers group events into cases and queue analysis.
4. RCA and actions are generated asynchronously.
5. A human reviews actions before rollback execution.
6. The system links the case to the latest stable deployment when it can.

## Deployment sources

Deployments can come from SDK payload metadata, manual API records, rollback
workflows, GitHub webhooks, or GitHub Actions sync. Each deployment can include
a source and external ID so the backend can process provider events
idempotently.

GitHub deployment records use these source values:

- `github_deployment` for GitHub deployment and deployment status events.
- `github_workflow_run` for GitHub Actions workflow run events and sync.

XecureCode does not treat a successful GitHub workflow as a stable release by
itself. A successful GitHub run becomes `ACTIVE`; it becomes `STABLE` only when
there is a healthy service check after the deployment time.

## Incident-to-deployment linking

The ingest worker links new events to deployments in this order:

1. Use the explicit `deploymentId` from the SDK payload when it belongs to the
   same service.
2. Match the payload `commitHash` to the latest deployment for the same service
   and environment.
3. Fall back to the latest `ACTIVE` or `STABLE` deployment for the same service
   and environment.

This linking gives RCA and rollback enough release context even when an SDK
doesn't send a deployment ID with every event.

## Access model

- Organization owners create services, manage organization settings, and control
  membership.
- Organization admins manage most organization and service collaboration tasks.
- Service owners and admins manage service settings, API keys, members, and
  rollback configuration.
- Members and viewers review assigned resources based on backend role checks.
